# 简介

  这篇主要写下，音频最基础的东西，最原始的东西，也是基础学科的东西， 哈哈哈。  以前学的物理，这个时候要体现了，以前没有学过这么深入的物理，哈哈哈。还是以了解基础为主吧。

# 开始

  声音变成数字，说穿了就两步。

  第一步把连续的波形按时间切成一个个点，
  第二步把每个点的高度用数字记下来。
  听起来简单，但音频行业所有的复杂性，都从这两步长出来。
  搞音视频开发的人，十有八九是从一个采样率参数开始懵的。
  打开 FFmpeg 命令行看到 -ar 44100，打开 WebRTC 看到 48000，再去查 AAC 文档，发现还有 8000、16000、22050 一堆。

## 声音的本质，其实是空气在抖

  你拍一下手，空气被挤压，往四周扩散。这股压力波传到耳朵里，鼓膜跟着抖，你就听见了"啪"。

  说话也一样。声带振动，推动周围的空气，形成一波一波的气压变化。如果把空气压力的变化画在纸上，横轴是时间，纵轴是压力大小，你就得到一条波形曲线。

  这条曲线长什么样？
  抖得快的，是高音
  抖得慢的，是低音
  抖得幅度大，声音响
  抖得幅度小，声音轻
  记住这一点，后面所有概念都建立在这条曲线上。

## 模拟信号和数字信号差在哪

  麦克风是把空气抖动转换成电压抖动的小机器。空气压力大，输出电压就高；空气压力小，电压就低。

  注意，这个电压是连续的。你可以无限放大某一段时间的细节，它永远有值，不会突然没了。这种波形我们叫模拟信号。

  但电脑、手机、网络里都不存连续的东西，它们只认 0 和 1。所以必须把这条连续的曲线，变成一串可以用二进制存储的数字。

  这个过程，就是数字化。

## 数字化的两步：切时间，量高度

  把连续波形变成数字，不是一步到位的，是两步：

### 第一步：采样（Sampling）

  每隔一小段时间，量一下波形当前的高度，记下来。其它时间的值，扔掉。

  打个比方，你想记录一辆车一天的位置。最准确的办法是 24 小时不间断盯着。但人盯不过来，那就改成每分钟看一次，记一个坐标。

  每分钟看一次，就是采样率为每分钟 1 次。每秒钟看一次，就是 1Hz。每秒钟看 44100 次，就是 44100Hz，也就是 44.1kHz。

### 第二步：量化（Quantization）

  每个采样点的高度，要用数字来记。问题是数字得有精度。

  如果只用 1 个 bit，那高度只能表示 0 或 1 两种状态，等于波形被压扁成方波，听起来跟摩尔斯电码一样难受。

  如果用 16 个 bit，就有 65536 个台阶。这就是 CD 音质的标准：16 bit 采样深度。

  如果用 24 个 bit，台阶数就是 1677 万级别，专业录音棚常用这个精度。

  形象点说：采样是把横向的连续滑梯切成阶梯，量化是把纵向的连续高度切成台阶。最后整条曲线变成一格一格的数字方块，就能用 0 和 1 存了。

## PCM 是什么？

  经过采样和量化两步之后，你得到的那一串整数数组，就叫 PCM，全称是 Pulse Code Modulation，脉冲编码调制。

  名字听起来很吓人，其实本质就是刚才那两步：把连续的模拟脉冲，按固定间隔采样，再用数字编码存下来。

  PCM 是整个数字音频世界的"通用语"。意思是：
  
  麦克风采集到的原始数据，就是 PCM
  耳机、扬声器最终播放的数据，也是 PCM
  MP3、AAC、Opus 这些压缩算法，压缩的是 PCM，解压完输出的还是 PCM
  FFmpeg 处理音频，绝大多数时候也是在各种格式和 PCM 之间转来转去
  
  所以搞音视频开发，你可以不知道 MP3 的压缩细节，但你必须知道 PCM 是什么。它是所有音频操作的起点和终点。

  有个常见的误区要澄清：WAV 不是 PCM。WAV 是一种容器格式，它只是给原始的 PCM 数据加了一个 44 字节的文件头，里面记录了采样率、位深、声道数这些信息，让播放器双击就能打开不用手动输参数。

## PCM 音频数据怎么处理？

  做音频开发，百分之八十的时间，你都是在跟 PCM 数据打交道。
  但很多人对 PCM 有一种莫名的恐惧，觉得是很底层、很复杂的东西。其实不是。
  PCM 是什么？就是一串整数数组而已。
  这篇不讲理论，直接给你可以复制粘贴运行的代码。三个最常用的操作：调音量、混音、静音检测。都是我实际项目里用的，拷过去就能用。

### 先搞清楚 PCM 的内存布局

我们默认说的 PCM，一般是 16 位有符号整数，也就是 s16le。每个采样点占 2 字节，范围是 -32768 到 32767。0 就是静音。

如果是单声道，内存就是这样的：[帧1][帧2][帧3][帧4]...
如果是双声道立体声，那就是左右声道交替存放：[左1][右1][左2][右2][左3][右3]...

这个叫 interleaved 模式，也是最常用的模式。FFmpeg、声卡、几乎所有的音频 API，默认都是这个布局。

记住这点很重要。处理双声道数据的时候，第 0、2、4...个采样是左声道，第 1、3、5...个是右声道。你想单独调左声道的音量，就只操作奇数或者偶数索引的采样点就行。

### 操作一：调节音量

  调音量是最简单也是最常用的操作。原理也简单：每个采样点乘以一个系数。系数 0.0 就是静音，1.0 就是原音量，2.0 就是两倍音量，0.5 就是一半音量。就这么简单。

 ``` C

// 调整 16 位 PCM 的音量
// data: PCM 数据指针
// sample_count: 采样点数量（双声道的话是总采样数，不是帧数）
// volume: 音量系数，0.0=静音，1.0=原音量，>1.0=放大，<1.0=缩小
void pcm_adjust_volume(int16_t* data, int sample_count, float volume) {
    for (int i = 0; i < sample_count; i++) {
        int32_t temp = (int32_t)data[i] * volume;
        // 钳位，防止溢出
        if (temp > 32767) temp = 32767;
        if (temp < -32768) temp = -32768;
        data[i] = (int16_t)temp;
    }
}

 ```

注意那个「钳位」操作。放大音量的时候，乘完可能会超过 16 位整数的范围。这时候必须把它钳到最大值，不然会溢出变成乱七八糟的数字，声音就爆了。
这个函数单声道和双声道都能用。双声道的话 sample_count 就是总采样数（采样率 × 声道数 × 秒数）。

进阶优化：如果要做音量的平滑过渡，比如 100 毫秒内从 0 线性升到 1.0，不要直接跳，那样会有爆音。每一帧的音量系数慢慢调。

``` C

// 平滑音量调整，每帧的音量系数比上帧多 step
void pcm_adjust_volume_smooth(int16_t* data, int sample_count,
                              float start_volume, float end_volume) {
    float step = (end_volume - start_volume) / sample_count;
    for (int i = 0; i < sample_count; i++) {
        float v = start_volume + step * i;
        int32_t temp = (int32_t)data[i] * v;
        if (temp > 32767) temp = 32767;
        if (temp < -32768) temp = -32768;
        data[i] = (int16_t)temp;
    }
}

```

### 操作二：混音

混音就是把多路 PCM 加起来。原理很简单：对应位置的采样点加起来就行。比如把 A 和 B 两路混合：结果[i] = A[i] + B[i]
但有个问题：两个 16 位整数加起来，最大值是 32767 + 32767 = 65534，已经超过 16 位的范围了。直接加会溢出。所以混音一般是先转成 32 位整数或者浮点，加完之后再转回来。

``` C

  // 把 input 混到 output 里，两路采样数相同
// 注意：如果 output 里已经有东西，input 是加在上面的。如果 output 是 0，结果就是 input。
void pcm_mix(int16_t* output, const int16_t* input, int sample_count, float input_volume) {
    for (int i = 0; i < sample_count; i++) {
        int32_t sum = output[i] + (int32_t)(input[i] * input_volume);
        // 还是要钳位
        if (sum > 32767) sum = 32767;
        if (sum < -32768) sum = -32768;
        output[i] = (int16_t)sum;
    }
}

```

这个函数可以多次调用，混多少路都可以。混第三路就再调一次。

常见的坑：很多新手混音的时候，怕溢出，会先把每一路都除以 N（N 是路数），比如两路就都除以 2。这样确实不会溢出，但也导致只有一路有声音的时候，音量自动变成原来的一半，声音忽大忽小。更好的做法是：用 32 位浮点或者 32 位整数做累加全部混完之后找整个 buffer 的峰值如果峰值超过 32767，整个 buffer 统一除以峰值做归一化。如果没超过，就不用动。这样只要不是所有路同时都满音量，就不会有损失


### 操作三：静音检测

  静音检测的目的是：如果这段音频是静音，就不用编码也不用发，省带宽。原理也很简单：计算一段时间内的平均能量或者峰值能量，低于某个阈值就算静音。最常用的是计算 RMS（均方根）：

``` C

// 计算 PCM 的 RMS 能量值
float pcm_calculate_rms(const int16_t* data, int sample_count) {
    if (sample_count <= 0) return 0.0f;
​
    int64_t sum = 0;
    for (int i = 0; i < sample_count; i++) {
        sum += (int64_t)data[i] * data[i];
    }
​
    float mean = (float)sum / sample_count;
    return sqrtf(mean);
}

```

RMS 值的范围是 0 到 32767。一般来说：

RMS < 100：基本就是静音，或者非常小声的背景噪音。
100 < RMS < 1000：小声说话。
RMS > 1000：正常说话或者更大声的声音。

静音检测就可以这么写：

``` C

// 检测是不是静音，返回 1 是静音，0 不是
// threshold 建议默认给 100-200，根据实际场景调
int pcm_is_silence(const int16_t* data, int sample_count, float threshold) {
    float rms = pcm_calculate_rms(data, sample_count);
    return rms < threshold ? 1 : 0;
}

```

很多时候你不会只要单个帧的结果，因为一帧 20ms，刚好在两个字中间，可能那一帧能量很低，但不是真的静音。
所以一般会加一个滞后机制：连续 N 帧都检测到静音，才真正认为是静音。静音结束之后，也要连续 N 帧有声音，才认为声音恢复了。防止断断续续的。

### 声道转换

#### 单声道转立体声

最简单的就是把左声道和右声道赋值成一样的就行。

``` C

void pcm_mono_to_stereo(const int16_t* mono, int16_t* stereo, int sample_count) {
    for (int i = 0; i < sample_count; i++) {
        stereo[i * 2] = mono[i];          // 左声道
        stereo[i * 2 + 1] = mono[i];      // 右声道
    }
}

```

#### 立体声转单声道

把左右声道加起来除以 2。

``` C

void pcm_stereo_to_mono(const int16_t* stereo, int16_t* mono, int sample_count) {
    for (int i = 0; i < sample_count; i++) {
        int32_t sum = stereo[i * 2] + stereo[i * 2 + 1];
        mono[i] = (int16_t)(sum / 2);
    }
}

```

### 几个常见的坑

  坑一：端序搞错了
  
  PCM 一般是小端（little-endian），低字节在前，高字节在后。x86 和 ARM 默认都是小端，所以大部分时候你不用管。但如果你是从某些设备或者文件里读出来的数据，一定要确认端序。大端小端搞反了，声音会变成一片噪音，根本没法听。
  
  坑二：以为 0 就是中间，其实 -1 和 1 才是最接近中间的
  
  很多人以为 0 是静音，没错。但以为范围是对称的：-32767 到 32767。其实不是。16 位有符号整数的范围是 -32768 到 32767。负数比正数多一个值。所以做缩放的时候，正的和负的要分开算，或者直接用 32 位整数做中间运算。
  
  坑三：浮点和整数之间的转换
  
  很多 DSP 算法是用浮点数算的。浮点数转整数的时候记得加 0.5 再取整，直接截断误差会比较大。
  
  坑四：忘记钳位

    只要做乘法、加法，就有可能溢出。只要有溢出的可能，就一定要钳位。少了钳位，偶尔会出现非常刺耳的爆音。这种 bug 很难复现，因为只有刚好溢出的时候才会出现。

### 总结 

  PCM 处理就是纯数字计算。没有什么魔法，也没有什么你理解不了的东西。本质上就是对一个整数数组做各种加减乘除。不要怕直接操作 PCM 数据。觉得算法对不对，写个小程序跑一下，把输入输出 dump 出来，画个图对比一下，立刻就知道了。很多音频工程师干了好几年，连一行直接操作 PCM 的代码都没写过，永远在用别人写好的库。碰到问题根本不知道怎么排查。这是不行的。亲手写一遍音量调节、混音、静音检测，你对音频的理解会上一个台阶。

## 三个参数，决定一段音频的"体质"

  刚才提到的两个参数，加上声道数，是数字音频的"三要素"。

  采样率（Sample Rate）：每秒采样多少次，单位 Hz。常见值 8000、16000、44100、48000、96000。
  位深（Bit Depth）：每个采样点用多少 bit 记录。常见值 8、16、24、32。
  声道数（Channels）：单声道是 1，立体声是 2，5.1 环绕声是 6。

  一段没压缩的原始 PCM 音频，文件大小怎么算？很简单：
  文件大小 (字节/秒) = 采样率 × 位深 / 8 × 声道数
  举个例子，CD 音质双声道： 44100 × 16 / 8 × 2 = 176400 字节/秒 ≈ 172 KB/秒

  一首 4 分钟的歌，PCM 原始数据约 41MB。这就是为啥 MP3 要压缩，1MB 的 MP3 听起来跟 10MB 的 PCM 差别不大，但传输成本天差地别。

## 为什么电话只用 8000Hz，CD 却要 44100Hz

  结论：采样率必须大于声音最高频率的 2 倍，才能完整还原。

  人说话主要频率范围是 300Hz 到 3400Hz，所以电话只要采样率超过 6800Hz 就够，工程上取 8000Hz。

  人耳能听到的频率上限是 20000Hz，所以采样率要大于 40000Hz。CD 取 44100Hz，留了一点余量。

  48000Hz 这个数字哪来的？是为了和视频帧率对齐。一帧 1/24 秒、1/25 秒、1/30 秒……48000 都能整除得很好，所以视频领域默认用 48000Hz。

## 几个常见的坑

  坑一：声道数搞错，声音会变快或变慢
  
  PCM 数据是裸流，没有任何头信息。如果一段双声道数据被你按单声道读，时长会算成一半。反过来，单声道当双声道读，会出现一边响一边没声音。
  
  坑二：位深和字节数别混
  
  16 bit 是 2 字节，24 bit 是 3 字节，32 bit 是 4 字节。算文件大小时，是除以 8 转字节，不是除以位深。

  坑三：大端小端搞反，声音变成噪声
  
  s16le 是小端，s16be 是大端。绝大多数 x86 和 ARM 是小端，搞反了你会听到一片白噪声。

  坑四：原始 PCM 没法直接播放
  
  双击 .pcm 文件不会有反应，因为没有头信息说明它的采样率和声道数。要播放得用 FFplay 指定参数：ffplay -f s16le -ar44100-ac1 test.pcm

## 为什么 CD 音质是 44.1kHz？一个 1928 年发现的定理统治了整个音频行业

  电影是怎么动起来的？一秒钟拍 24 张照片，然后按顺序快速播放。你的眼睛和大脑会把这 24 张静态图片脑补成连续的动作。
  那如果一秒只拍 3 张呢？那看电影就跟看 PPT 一样，一卡一卡的。信息丢了。
  拍得越快，动作越流畅。一秒 60 张，玩游戏的时候你就会觉得跟真的一样。
  音频采样是一模一样的道理。
  你把声音的波形，想象成一个人跑步的轨迹。你每隔一段时间拍一张照片，拍得够快，把照片连起来就能还原出完整的跑步动作。拍慢了，轨迹就断了，还原出来的东西跟原版差远了。
  这个「每秒拍多少张照片」，放在音频里就叫采样率。

### 那最少要拍多少张才够？

  1928 年，有个叫奈奎斯特的工程师，在贝尔实验室算了一笔账。
  他说，假设原始信号里最高的频率是 f，那你只要用大于 2f 的速度去采样，就能完美还原出原始信号。少一点都不行。
  这个结论后来被人叫做奈奎斯特采样定理。别担心，我不会给你推公式。给你举个例子你就懂了。
  假设一个正弦波，一秒钟来回震荡 2 次（频率 2Hz）。你最少要采几个点才能还原出这个波形？
  答案是 4 个。不对，是大于 4 个。哦不对，准确说是大于 2 倍。你要是正好每秒采 2 个点，运气不好的话两个点都采在零线上，得到的就是一条直线。

### 那 20000Hz 是怎么回事？

  人耳能听到的声音频率范围，大概是 20Hz 到 20000Hz。
  低于 20Hz 的叫次声波，地震那种。高于 20000Hz 的叫超声波，医院 B 超那种。正常人都听不到。
  那按照奈奎斯特的定理，要完整还原人耳能听到的所有声音，采样率就得大于 40000Hz。也就是 40kHz 以上。
  听到这里你是不是觉得哪里不对？既然大于 40kHz 就行，那为什么 CD 选了 44.1kHz，不是 44kHz，不是 45kHz，不是整数？
  我当时查到这里也懵了。44100 这个数字怎么看都像是拍脑袋随便定的。

### 那 48000 又是怎么来的？

  既然有 44100 了，为什么还有个 48000？
  这个跟视频有关。
  电影是 24 帧每秒，电视 PAL 制是 25 帧，NTSC 是 30 帧。做视频的时候，每帧画面对应的音频采样数最好是整数，不然同步会出问题。
  48000 除以 24、25、30 都是整数。44100 就不行，除完都是小数。
  所以视频行业、广电行业统一用 48000Hz。现在你知道为什么做视频剪辑的时候，导入的音频素材如果是 44100 的，软件总会提醒你转成 48000 了吧？
  
  不是谁比谁好，就是两个不同阵营的历史遗留问题。

### 那采样率是不是越高越好？

  很多发烧友说 96kHz 比 44.1kHz 音质好，192kHz 更是听了能上天。
  说实话，我盲听分不出来。我认识的很多做了十几年音频的工程师，也分不出来。
  理论上采样率越高，还原的波形越接近原始。但问题是，你的耳朵只能听到 20kHz 以下的声音。采样率再高，多出来的那些频率你也听不到。
  当然，专业录音棚用 96kHz 甚至 192kHz 是有道理的。后期处理的时候余量更大，做多段压缩、EQ、混响的时候失真更小。
  但你做个短视频配个背景音乐，或者开个线上会议，44100 完全够用。
  真的。别在这上面瞎纠结。我见过好多新人天天纠结用 44100 还是 48000，代码一行没写，参数倒是研究了半个月。没必要。

### 几个常见的坑
  
  第一个坑，音频重采样。你把 44100 的音频转成 48000，或者反过来，音质一定会损失。不管用多好的算法都没用。所以源文件是什么采样率，就一直用到底，别没事转来转去。
  第二个坑，WebRTC 安卓端有些老设备，只支持 48000Hz。你给它喂 44100 的数据，要么没声音，要么声音跟机器人一样。别问我怎么知道的。
  第三个坑，FFmpeg 的 -ar 参数，如果你不写，它有时候会自动给你转成 44100。出来的文件音质不对，你找半天原因，最后发现是默认参数搞的鬼。

## 从麦克风到耳机的延迟：音频链路每一环到底花了多少毫秒？

  做实时音频的人，这辈子都在跟延迟打仗。
  用户说「我怎么感觉有延迟」，是所有开发者的噩梦。但你去问他「延迟有多少？」，十有八九答不上来。是 100ms？300ms？还是 1 秒？
  大部分人对延迟没有量化的概念，只知道「感觉有点卡」。
  这部分就把整个音频链路，从你对着麦克风说话，到对方从耳机里听到声音，每一环花了多少毫秒，给你拆解得明明白白。
  看完你就知道：延迟到底来自哪里，哪些地方可以优化，哪些是物理极限，神仙来了也改不了。

### 先搞清楚一个概念：人能感知到多少延迟？

  先给你几个基准值，看完你就知道我们在跟什么打仗：

- 低于 20ms：人类完全感知不到。跟面对面说话没区别。
- 20-80ms：非常优秀的水平。你只会觉得对方反应很快，根本感觉不到有延迟。
- 80-150ms：良好。大部分视频会议软件在这个区间，正常对话没问题。
- 150-300ms：可以感知到延迟，但还能正常交流。300-500ms：明显觉得慢了，两个人说话会经常抢话。
- 超过 500ms：没法正常对话了，必须说完等一下对方回应。
- 超过 1 秒：跟打卫星电话差不多，体验很差。
  
所以我们的目标是什么？端到端延迟控制在 150ms 以内，最好 100ms 以内。

### 整个音频链路的延迟拆解

从你说话，到对方听到声音，一共要经过 9 个环节。我们一个一个数。

#### 1. 声速传播：1 ms/34 厘米

  这是最容易被忽略，但也是最无解的延迟。
  
  声音在空气中的传播速度是 340 米/秒，也就是每 34 厘米需要 1 毫秒。
  你离麦克风 30 厘米，光声音从你嘴里传到麦克风就要 1ms。两个人在同一个房间里说话，光声音在空气中传播就要 3-5ms。
  这是物理定律，没有任何优化的可能。除非你把麦克风直接贴在嘴上。好在这个延迟一般很小，不是主要问题。
  延迟：1-5 ms能否优化：不能，物理定律

#### 2. 麦克风采集：5-20 ms

  麦克风把声音的模拟信号，转成数字的 PCM 信号。
  这个转换本身很快，慢的是操作系统的音频栈。
  操作系统不会来一个采样点就给你一个采样点。那样太费 CPU 了。它会攒够一定数量的采样点，再一次性给你。
  这个「攒多少」的缓冲，就是采集延迟的主要来源。
    Windows 专业音频驱动（ASIO）：可以做到 5-10ms。
    macOS/iOS 音频栈：优化得很好，一般 5-15ms。
    Windows 普通音频驱动（WDM/MME）：10-30ms。
    Android：那就没谱了，从 10ms 到 200ms 的都有，看厂商良心。
    Android 音频延迟是出了名的烂。
    
  延迟：5-200 ms，取决于平台和硬件能否优化：可以，调小采集 buffer。但太小了容易爆音。Android 优化空间最大。

#### 3. 前处理（AEC/ANS/AGC）：5-10 ms

  3A 算法。简单说就是回声消除、噪声抑制、自动增益控制。
  这些算法都需要一点时间窗口来处理数据。比如回声消除，需要参考信号和输入信号做对齐，这个对齐本身就需要几个毫秒的缓冲。
  好的算法（比如 WebRTC 的 AEC3）引入的延迟大概 5ms 左右。烂的算法可能要 20ms 以上。
  
  延迟：5-10 ms能否优化：可以，换更好的算法。但不能完全去掉。
  
#### 4. 编码：5-60 ms

编码就是把原始的 PCM 压缩成编码包。延迟主要来自两部分：
  1. 编码器本身的算法延迟。比如 Opus 20ms 帧，算法本身大概需要 1-2ms 就能编完。
  2. 帧长。这个是大头。你用 20ms 的帧长，编码就得等 20ms 的数据攒齐了才能开始编。

帧长是编码延迟最主要的来源。
  Opus 2.5ms 帧长：总延迟 3ms 左右
  Opus 20ms 帧长：总延迟 22ms 左右
  AAC-LC：23msG.729：10ms
  MP3：24ms
  
  这就是为什么实时通话绝对不能用 MP3 或者 AAC。光编码延迟就比人家整链路都高了。
  
  延迟：3-60 ms，取决于编码和帧长能否优化：可以，用更小的帧长。但帧越小，压缩率越差，码率越高。Trade-off。

#### 5. 发包抖动缓冲：0-50 ms（平均 10-20ms）

  编码完了不会立刻发出去。操作系统的网络栈会把几个小包攒成一个大包再发，提高网络效率。
  
  这个叫 Nagle 算法。
  
  实时通话的时候一般会把 Nagle 关掉，有包就发。但还是会有几个毫秒的网络栈延迟。
  
  如果是做视频会议，很多系统会把几个音频包攒成一个 UDP 包发出去，进一步减少网络开销。这个也会增加延迟。
  
  延迟：1-50 ms能否优化：可以。关 Nagle，不要攒包，有一个发一个。但网络开销会变大。

#### 6. 网络传输：20-200 ms

  这个是大部分人最熟悉的延迟。
    同一个城市：20-30ms
    跨城市：30-50ms
    跨国：100-200ms
    卫星链路：500ms+
  
  光在光纤里的传播速度是 20 万公里/秒，绕地球一圈大概 200ms。这个也是物理极限。
  网络延迟还有两个更讨厌的东西：抖动和丢包。
    抖动：有时候 20ms 到，有时候 80ms 到，忽快忽慢。
    丢包：100 个包里面丢几个。
  这两个才是实时音频的大敌。为了对抗它们，我们需要下一个东西：Jitter Buffer。
  
  延迟：20-200+ ms能否优化：可以，选好的线路，离用户近的服务器。但物理极限在那，不可能无限低。（GA加速，边缘服务器接入，骨干网传输）

#### 7. Jitter Buffer（抖动缓冲）：20-200 ms

  这是整个链路里最大的延迟来源之一，也是最容易被忽略的。
  
  网络包不是均匀到达的。第 1 个包 20ms 到，第 2 个 50ms 到，第 3 个 30ms 到。如果来一个就播一个，声音就会忽快忽慢，卡成电音。
  
  所以我们需要一个缓冲：先把包接进来放一会儿，等它几毫秒，然后用一个均匀的速度往外播。把网络的抖动「熨平」。
  这个缓冲的大小，直接决定了延迟。
  缓冲设 20ms：延迟低，但网络一抖动就容易空，声音就卡。缓冲设 200ms：很稳，基本不会卡，但延迟高到没法正常对话。
  好的 Jitter Buffer 是动态的。网络好的时候自动缩小缓冲，网络差的时候自动扩大。WebRTC 的 Jitter Buffer 就是动态的，正常网络下大概 20-40ms，网络差的时候会自动涨到 100ms 以上。
  
  这就是为什么你网络差的时候，会觉得对方反应越来越慢。不是对方变慢了，是你的缓冲变大了。
  
  延迟：20-200+ ms，这是整个链路最大的变量能否优化：可以，这是优化的重点。好的 Jitter Buffer 算法可以在延迟和稳定性之间找到最好的平衡。

#### 8. 解码：2-10 ms

  解码比编码快。因为解码的计算量一般只有编码的 1/3 到 1/2。
  Opus 解码一帧 20ms 的数据，大概 1ms 就够了。
  
  延迟：2-10 ms能否优化：可以，但空间不大。瓶颈不在这。

#### 9. 播放缓冲：10-50 ms

  跟采集端一样。解码出来的 PCM 不会立刻交给声卡。要先放到播放缓冲里，攒够一定的数据再播，防止中间断了。
  
  这个缓冲的大小，也是平台决定的。专业音频设备可以做到 5ms 以下，手机一般 10-20ms，垃圾 Android 手机可能 50ms 以上。
  
  延迟：5-50 ms能否优化：可以。调播放 buffer 大小。Android 又是重灾区。

#### 加起来一共多少？

  我们把每一环的最优情况加起来：
  1.声速：2ms
  2.采集：10ms
  3.前处理：5ms
  4.编码：20ms
  5.发包：2ms
  6.网络：30ms
  7.Jitter Buffer：20ms
  8.解码：2ms
  9.播放：10ms
  
  总计：101 ms

  这就是理论上的最优值。实际产品中能做到 150ms 以内，就已经是行业顶尖水平了。

  目前ai陪聊这个方向，基本上是1s+， 全模态的也不能达到150ms以内， 三段式的架构就更不用说了。

#### 最容易优化的三个地方

  看完拆解你就知道，大部分优化工作都是在做这三件事：

##### 1. 把采集和播放的 buffer 调小  

  这是回报最高的优化。很多产品默认的采集 buffer 就是 100ms，你改成 20ms，延迟立刻降 80ms，零成本。
  唯一的副作用是 buffer 太小了容易爆音，也就是音频卡顿。需要在不同的机型上测试，找到一个不卡的最小值。
  Android 这里的坑特别多，不同厂商、不同型号、不同系统版本，最优值都不一样。很多人的青春都耗在这上面了。

##### 2. 优化 Jitter Buffer 算法

  Jitter Buffer 是整个链路延迟最大的变量。好的算法和差的算法，能差出 100ms 的延迟。
  WebRTC 的 NetEQ 算法是目前公开的最好的 Jitter Buffer 实现。如果你的产品还在自己写 Jitter Buffer，别写了，直接把 NetEQ 抄过去就行。

##### 3. 降低编码帧长

  Opus 支持 2.5ms、5ms、10ms、20ms、40ms、60ms 帧长。
  你现在用的是 20ms，改成 10ms，编码延迟立刻降一半。改成 5ms，再降一半。
  代价是什么？帧越小，压缩率越差，同样音质需要更高的码率。2.5ms 帧长的码率，比 20ms 帧长大概高 30-40%。
  如果你的网络带宽足够，用小帧长绝对是值得的。延迟降下来的体验提升，远大于那点带宽成本。

#### 几个常见的误区

  误区一：延迟越低越好。
    不是。延迟太低了，Jitter Buffer 就小，稍微有点网络抖动就会卡。用户宁可要延迟高一点但声音不卡，也不要延迟低但经常断。稳定比低延迟更重要。
  误区二：我把所有 buffer 都调到最小，延迟就最低了。
    最小的延迟，是根本不做缓冲，来一个包就播。但网络只要有一抖动，立刻就卡成电子音。用户不会夸你延迟低，只会骂你声音卡。
  误区三：优化编码算法能大幅降低延迟。
    编码本身只占整个链路的不到 10%。编码算法再优化，也就能省个 1-2ms，跟 Jitter Buffer 的几十上百毫秒比，根本不是一个量级的。优化的重点永远是采集、播放、Jitter Buffer，还有网络。

#### 总结

  做实时音频，本质上就是在三个东西之间做平衡：延迟、音质、稳定性
  你最多只能同时优化两个，不可能三个都做到最好。
  要最低延迟，就要牺牲一点稳定性和音质。要最好的音质，就要牺牲一点延迟。
  要最稳定，什么网络都不卡，就要接受高一点的延迟。
  没有完美的方案，只有最适合你场景的方案。
  能把这个平衡做好，就是顶尖的工程师了。
