# 开始

## 容器格式的真相

  很多新手分不清「容器格式」和「编码格式」。
  看到一个 .mp4 文件，就说「这个视频是 MP4 编码」。
  不对。
  MP4 是容器，不是编码。容器里面装的视频轨、音频轨、字幕轨，这些东西的编码格式，才是真正的编码。
  这篇就把容器这件事彻底讲清楚。看完你就知道，为什么同样内容，存成 MKV 比 MP4 小，为什么网络播的视频都用 TS 格式。

## 容器是什么？

  你可以把视频文件想象成一个快递包裹。
  视频轨是你的商品
  音频轨是赠品
  字幕轨是
  说明书容器就是那个纸箱子

  箱子的作用，就是把这些东西装在一起，按顺序摆好，然后在箱子上写清楚：第 10 秒该播哪个视频帧，对应的声音是哪一帧，字幕是什么。

  你打开视频文件的时候，播放器就是快递员，照着箱子上写的说明，按顺序把里面的东西掏出来给你看。
  所以容器不决定画质，只决定「能不能装」和「装起来方便不方便」。

  同样的视频，同样的编码，存成 MP4 和存成 MKV，画质是一模一样的，只是文件大小可能略有区别，兼容性不一样。

## MP4 容器底层：Box 结构

  MP4 的内部结构不是流水账，而是一棵嵌套的树。组成单元叫 Box（盒子），也叫 Atom，每个 box 长这样：

  [size: 4字节][type: 4字节][data: size-8 字节]
  
  size 是整个 box 的大小（含自己），
  type 是 4 个 ASCII 字符的类型标识。
  Box 之间可以嵌套——比如 moov 里装 trak，trak 里装 mdia，mdia 里装 minf……这是个深度优先的树形结构。

  一个最简单的 MP4 文件，至少有这三个顶层 box：
  ftyp（File Type Box）： 文件类型与兼容性声明（必须在文件最前面）
  moov（Movie Box）： 所有元数据（时长、轨道、采样表、关键帧位置）
  mdat（Media Data Box）：真正的音视频原始数据

  moov 是 MP4 的灵魂。它里面有每一帧的字节偏移（stco/co64）、每一帧的大小（stsz）、关键帧索引（stss）、时间戳（stts）。
  没有 moov，整个文件就是一堆 H.264/AAC 字节，播放器无从下手。

## 常见的容器格式有哪些？

  我给你盘点一下主流的几个：

### MP4（.mp4 / .m4v）

  目前最通用的格式，没有之一。
  所有平台、所有设备、所有浏览器，都支持 MP4。你把一个 MP4 文件发给任何人，不管他用手机、电脑、电视，基本都能打开。
  MP4 的优点是标准化好，兼容性好，文件也不大。缺点是扩展性差，不支持很多高级功能，比如很多字幕格式装不了，音视频轨的数量也有限制。

### MKV（.mkv）

  开源社区的宠儿。
  特点就是啥都能装。视频、音频、字幕，不管什么格式，都能往里塞。一个 MKV 文件里装十几条音轨、几十条字幕，都是常规操作。
  你下载的电影、美剧，基本都是 MKV 格式，就是因为它能同时装好多条国配、英配、字幕。缺点是兼容性差。很多智能电视、车载播放器不支持 MKV，浏览器也基本不支持。

### TS（.ts）

  全称 MPEG-2 Transport Stream，流媒体界的王者。
  这个格式设计出来，就是为了在不可靠的网络上传输的。它把视频切成一个个 188 字节的小包，每个包都有自己的时间戳。
  好处是什么？就算中间丢了几个包，后面的还能正常播。你看直播的时候，网络卡了一下，后面恢复了还能继续看，就是 TS 的功劳。
  所有 IPTV、数字电视、直播流，基本都是 TS 格式。
  HLS 切片，切出来的小文件也都是 TS。缺点就是 overhead 略大，同样的内容，TS 文件比 MP4 大概大 1-2%。
  
#### TS 包结构与 PCR 时钟

  TS 为什么能扛丢包？因为它把数据切成 固定 188 字节 的包，每个包都自带寻找点。一个 TS 包的结构是这样的：
  | sync(0x47) | flags & PID (3字节) | adaptation field (可选) | payload |
      1 字节         3 字节                变长                    剩余

   sync_byte = 0x47：固定值，丢包恢复时满文件扫描 0x47 + 检查后续 188 字节是不是也是 0x47，就能找到下一个包的起点
   PID（13 bit）：标识这个包属于哪条流——视频 PID、音频 
   PID 都不一样
   adaptation field 可选携带 PCR（Program Clock Reference），这是 TS 的核心时钟

  PCR 的数学：TS 用 27 MHz 的时钟（=33 bit base × 1/90000 秒 + 9 bit extension × 1/27000000 秒）

  每个流的 PTS/DTS 都参考 PCR 来定时。播放器收到 TS 包后，用 PCR 校准自己的本地时钟，再按 PTS 决定什么时候显示哪一帧。
  这就是为什么数字电视能把多个频道的视频/音频/字幕揉在一条 TS 流里——大家都用同一个 PCR 时间基。

  这就是 TS 流抗丢包的本质：每 188 字节有一次"重新对齐"的机会。MP4 一旦中间损坏，后面整段就解不了，因为 moov 里的字节偏移全乱了。

### FLV（.flv）

  Flash 时代的遗物，RTMP 协议的标配。
  当年国内的视频网站全用 FLV。现在 Flash 已经死了，FLV 也基本淘汰了。只有一些老的直播系统还在用。新项目就别用了。

### MOV（.mov）

  苹果家的格式，跟 MP4 是亲兄弟。都是基于 QuickTime 容器发展出来的，本质上区别不大。Mac 和 iOS 生态里用的多，Final Cut Pro 导出默认就是 MOV。

## 怎么选容器？

  给你一个简单的决策树：
    - 要发给别人看，要上传视频平台：选 MP4，H.264 + AAC，99% 的设备都能播。
    - 自己存电影、做备份，要装多条音轨字幕：选 MKV。
    - 做直播、流媒体、IPTV：选 TS。
    - 苹果生态内部用：选 MOV。
    - 老项目兼容：FLV。啥也不懂就选 MP4，永远不会错。
  就这么简单。

## 容器最坑的地方：不是所有 MP4 都一样

  这是很多人踩过的坑。
  同样是 .mp4 后缀，里面的东西可能天差地别。
  比如：
  视频可以是 H.264，也可以是 H.265，还可以是 AV1、MPEG-2、VC-1。
  音频可以是 AAC，也可以是 MP3、AC3、DTS、Opus。
  甚至可以视频是 H.265，音频是 AC3，你电脑装的解码器正好不支持 H.265 或者 AC3，结果就是文件能打开，但要么没画面要么没声音。
  所以不要看见 .mp4 就觉得一定能播。后缀名只是个名字，真正重要的是里面的轨用的是什么编码。
  还有一个坑叫「Progressive vs Fragmented MP4」。
  普通的 MP4，所有的元数据（时长、码率、关键帧位置）都存在文件头里。播放器必须先把整个文件头读完，才能开始播。
  所以你播一个大的 MP4，点开之后要等几秒，缓冲完头才能播。碎片化 MP4（fMP4）不一样。它把元数据打散，存在每个片段里。边下边播，不用等整个头下载完。
  现在的 DASH 协议，还有油管、B站的网页播放器，用的都是 fMP4。你看那些长视频，点开就播，不用等，就是这个原因。

## 封装和解封装是什么？

  你经常听到「封装」和「解封装」这两个词，其实特别简单。
  把视频帧、音频帧、字幕按规则装进箱子里，就是封装。FFmpeg 里叫 mux（multiplexer）。
  把箱子拆开，把视频帧、音频帧、字幕拿出来，就是解封装。FFmpeg 里叫 demux（demultiplexer）。
  封装和解封装，只是把东西拿出来放进去，不改变内容本身。所以是无损的，速度也特别快。
  你用 FFmpeg 把 MKV 转成 MP4，如果参数里写 -c copy，就是直接把里面的视频和音频拷出来，重新装成 MP4 的箱子。几秒就能转完一个几 GB 的电影，画质没有任何损失。
  只有你重新编码的时候，才会损失画质。

## fMP4：DASH/HLS-fMP4 的基石

  fMP4（Fragmented MP4）把流切成一段段独立的 moof + mdat，每段自带元数据。这样可以一边录制一边切片下发，配合 HLS-fMP4 或 DASH 做直播。

## 小结

  容器格式这个东西，是整个音视频体系里最没有技术含量，但坑最多的部分。
  说它没技术含量，是因为本质上就是个数据打包的格式，规定了哪个字节存什么东西而已。
  说它坑多，是因为格式太多、变种更多。同样叫 MP4，有的能播有的不能播，有的拖动能秒开有的要等三秒。
  但对于 99% 的人来说，你根本不需要懂那么多。
  记住一句话就行：普通用户用 MP4，收藏用 MKV，直播用 TS。就这一句话，能解决你 99% 的问题。

## 别再混淆封装格式和编码格式了

  「这个视频是 H.264 还是 MP4？」「我把 AVI 转成 MP4，画质能提升吗？」「为什么我这个 MP4 文件，播放器打开只有声音没有画面？」
   所有这些问题，根源都是一个：搞混了「封装格式」和「编码格式」。这两个概念不搞清楚，后面的路会越走越歪。

### 一句话讲清楚区别

  先给你一个最简单的结论，记住就行：
  
  封装格式 = 箱子。决定了文件后缀名（.mp4、.mkv、.ts）。
  编码格式 = 箱子里装的东西。决定了视频是怎么压缩的（H.264、H.265、AV1）。
  封装格式和编码格式，是完全独立的两件事。
  同样的视频编码（比如 H.264），你可以装在 MP4 里，可以装在 MKV 里，可以装在 TS 里，甚至可以装在 FLV 里。

  同样的 MP4 文件，里面的视频可以是 H.264，可以是 H.265，也可以是 MPEG-2，甚至可以是 VP9。箱子不决定里面装什么东西。箱子只决定你怎么把东西摆进去。

### 编码器内部到底在干什么？
  
  很多人知道 H.264 是压缩视频，但不太清楚它具体在压缩什么。
  视频编码器其实就做四件事：
    1. 预测（Prediction）：用已经编好的像素，猜当前像素大概长什么样。猜得越准，需要存的信息就越少。
    2. 变换（Transform）：把残差（真实值和猜测值的差）从空间域转到频域，方便分离重要信息和不重要信息。
    3. 量化（Quantization）：把不重要的高频信息丢掉。这一步是有损的，也是画质损失的主要来源。
    4. 熵编码（Entropy Coding）：把剩下的数字用更短的二进制表示。这一步是无损的，只是压缩存储。

#### 变换：DCT 的数学本质

  H.264、H.265、AV1 都用了 DCT（离散余弦变换）或其变种。
  DCT 的意义在于：自然图像的能量大部分集中在低频。变换后，右下角的高频系数经常接近 0，量化时可以直接丢掉。

#### 量化：画质损失的真正来源

  量化是不可逆的。一旦高频信息被量化成 0，反量化也还原不回来。所以重新编码一定会损失信息，-c copy 才那么重要。

#### 熵编码：CABAC vs CAVLC
  
  H.264 有两种熵编码：
    CAVLC（Context-Adaptive Variable Length Coding）：基于查表，速度快，压缩率一般。Baseline Profile 只能用这个。
    CABAC（Context-Adaptive Binary Arithmetic Coding）：算术编码，压缩率高 10%-20%，但计算量大。Main/High Profile 才支持。
    
  现代编码器（x264、x265）默认用 CABAC，因为 CPU 解码成本早就不是瓶颈了。

### 为什么 90% 的人会搞混？

  因为大部分视频文件的后缀名，正好也是它最常用的编码。
  比如你看到 .mp4，里面大概率是 H.264 + AAC。看到 .flv，里面大概率也是 H.264 + AAC。看到 .mkv，大部分时候也是 H.264。
  慢慢的，大家就把「后缀名」和「里面的编码」画上了等号。
  但这是错的。
  MP4 只是个箱子，里面装什么编码都行。你可以把 H.265 视频装在 MP4 里，也可以把 AV1 装在 MP4 里，甚至可以把老掉牙的 MPEG-2 装在 MP4 里。
  只要播放器支持这个编码，就能播。
  不支持，就播不出来。
  这就是为什么有时候你拿到一个 .mp4 文件，双击打开，只有声音没有画面。不是文件坏了，是你的播放器不支持里面的视频编码。

### 坑点

  1.一个经典的坑：「我转格式为什么这么慢？」

  很多新人转格式的时候，会直接这样写命令：
  ffmpeg -i input.mkv output.mp4
  然后就看着进度条一点一点走，一个 10GB 的电影要转半小时。
  其实你根本不需要重新编码。你只是把 MKV 这个箱子拆开，把里面的 H.264 视频和 AAC 音频拿出来，重新装到 MP4 这个箱子里而已。
  东西本身没变，只是换了个箱子。这种操作叫「流复制」（stream copy），FFmpeg 里加个 -c copy 参数就行：
  ffmpeg -i input.mkv -c copy output.mp4
  几秒钟就搞定，画质没有任何损失。
  绝大多数人不知道这个参数，转格式的时候让 FFmpeg 把视频重新编码了一遍，白白浪费半小时，还损失了画质。
  这个坑，我敢说 90% 的人都踩过。

 2. 为什么我转成 MP4 还是播不了？

  很多人遇到播放器放不了视频，第一反应就是「我把它转成 MP4 就好了」。
  不一定。
  你转了 MP4，只是换了个箱子。如果里面的视频编码是 H.265，而你的老电视或者老播放器不支持 H.265，那还是播不了。
  换箱子解决不了编码不支持的问题。这时候你才需要重新编码，把 H.265 转成 H.264：
  ffmpeg -i input.mp4 -c:v libx264 -c:a copy output_h264.mp4
  这个命令的意思是：视频重新编码成 H.264，音频直接复制，不重新编码。
  这样转出来的文件，99% 的设备都能播。

### 常见的封装和编码组合

  给你列一下现在最常见的组合，心里有个数：

  MP4：H.264/H.265，AAC，通用、上传视频平台、发给别人看
  MKVH: .264/H.265/AV1,AAC/AC3/DTS/FLAC,收藏电影、多音轨多字幕
  TSH: .264/H.265,AAC/MP3,直播、IPTV、HLS
  WebM: VP9/AV1,Opus,网页视频、Chrome / 油管
  FLV: H.264, AAC/MP3, 老 RTMP 直播系统

注意：这些只是「最常用」的组合，不是唯一组合。
理论上任何编码都能装进任何容器，只是兼容性有好有坏。
比如你非要把 AV1 视频装在 FLV 里，技术上也能做到。
但没有任何播放器会认这种奇葩组合，等于做了个没用的文件。

### 几条实用建议

  1. 永远不要用后缀名判断编码。 用 ffprobe 看，这是唯一靠谱的方法。
  2. 只是换封装的时候，一定加 -c copy。 省时间，还不损失画质。发给别人的视频，统一用 H.264 + AAC + MP4。 这是兼容性最好的组合，任何设备都能播。不要用 H.265，很多老设备播不了。
  3. 不要迷信「格式越新越好」。 AV1 压缩率确实高，但 2020 年之前的电脑和手机，硬解 AV1 的没几个。发给别人的视频，兼容性永远是第一位的。
  4. 转格式之前先想清楚：我是要换箱子，还是要换里面的东西？ 前者用 -c copy，后者才需要重新编码。
  5. 做 WebRTC 的时候，封装和编码耦合得更紧。 选 H.264 还是 VP8，不只是"画质更好"的问题，还决定了 RTP payload 的打包方式和对方的解码能力。协商失败就会导致黑屏。

封装和编码的区别，听起来是个很简单的概念。但就是这么简单的一个概念，不知道坑了多少人。
很多人做了一两年视频开发，还在犯「转格式不加 -c copy」的错误。还在问「为什么我这个 MP4 播不了」。
基础不牢，地动山摇。把基础概念搞清楚，能帮你少走很多弯路。
