# 开始

## 音视频压缩到底在压什么？

  怎么把这些数据变小，还尽量不影响体验。
  这是整个音视频领域最核心的问题。所有的标准、算法、专利、商业战争，本质上都是围绕这件事展开的。
  先问你一个问题：如果网络和硬盘都是无限大的，我们还需要压缩吗？
  当然不需要。
  直接传原始的 PCM 音频和 RGB 视频就行，什么音质损失、画质损失，通通不存在。
  但现实是：
    44.1kHz 16bit 双声道音频，一秒钟 172KB，一分钟 10MB，一首歌 40MB。
    1080p 30fps 的视频，一秒钟 180MB，一分钟 10GB。
    4K 60fps 的视频，一秒钟 1.4GB。

  你用 4G 网络看，一秒钟要下 1.4GB 的数据，看一分钟话费就没了。
  所以压缩不是一个技术选择，是被物理现实逼的。

  所有的编解码器——不管是 MP3、AAC、Opus，还是 H.264、H.265、AV1——干的都是同一件事：在尽量不影响听感/观感的前提下，把数据压到最小。

  这句话里有两个关键词：「尽量不影响体验」和「压到最小」。这两个目标是矛盾的。
  整个编解码领域一百多年的发展史，就是在这两个目标之间找平衡的历史。

### 压缩为什么可能？因为有冗余

  原始的音视频数据里，有大量重复的、可以删掉的东西。这些重复的东西，我们叫「冗余」。
  音频里的冗余是什么？
  举个最简单的例子：左右声道大部分时候是差不多的。你不需要完整存两份，存一份完整的，再存两份的差值就行。差值一般很小，用很少的 bit 就能存下来。MP3 和 AAC 里的「联合立体声」就是这么干的。
  还有更大的冗余：人耳听不到的声音。
  人耳能听到的频率范围是 20Hz 到 20kHz。超过 20kHz 的超声波，你听不到。
  那编码器直接删掉就行，反正你也听不出来。
  还有更绝的：就算是在 20-20kHz 范围内的声音，也不是所有你都能听到。一个很大的声音旁边，如果有个很小的声音，你是听不到的——这叫「听觉掩蔽效应」。
  编码器就专门找这些你听不到的声音，毫不留情地删掉。
  这就是心理声学模型，是所有音频压缩的核心。

### 视频里的冗余就更多了

  视频是一帧一帧的图片，相邻两帧长得几乎一模一样。
  两个人在对话的视频，背景可能一分钟都不变。只有嘴在动，其他地方都是一样的。
  那我为什么要每一帧都完整存一遍？
  我存第一帧完整的，后面的帧只存「和前一帧不一样的地方」不就行了？
  这就是帧间压缩。也是 H.264 能把 180MB 每秒的原始视频压到 2Mbps 的核心秘密。
  还有帧内的冗余：一块蓝色的天空，每个像素的值都差不多。不需要每个像素都存，存一个基准值，再存差值就行。
  这就是帧内压缩。
  压缩算法的本质，就是想尽一切办法，找到数据里所有的冗余，把它们删掉。
  删得越狠，文件越小。删错了地方，你就会听出失真、看出马赛克。
  好的编码器和差的编码器，差距就在于：同样的文件大小，好的编码器删的都是你注意不到的东西，差的编码器把你看得很清楚的地方给删了。

### 有损压缩 vs 无损压缩

  这是一个最基本的分类。
  无损压缩： 压缩之后解压出来，和原始数据一模一样，一个 bit 都不差。
  代表格式：FLAC、ALAC、ZIP、PNG。
    优点：音质/画质没有任何损失。
    缺点：压缩率有限。一般最多能压到原来的 1/2，想再小不可能了。
  什么时候用？
    做母带、做存档，以后还要反复编辑处理的。
    发烧收藏，追求最原始的音质。
  有损压缩： 压缩之后解压出来，和原始数据不一样了。有损失，但是人耳/人眼尽量察觉不到。
  代表格式：MP3、AAC、Opus、H.264、H.265、AV1、JPEG。
    优点：压缩率极高。10 倍、20 倍、100 倍都有可能。
    缺点：有损失，虽然你可能听不出来看不出来。而且是不可逆的，压完了就再也回不去了。
  什么时候用？
    分发、传播、给普通人看的。
    在线视频、短视频、直播、在线音乐。
  99% 的场景，我们用的都是有损压缩。
  不是无损不好，是真的没必要。

### 两个常见的误区

  误区一：无损一定比有损好。
    分情况。如果你是收藏、做后期，无损确实好。如果你只是自己听、自己看，320kbps 的 AAC 和无损 FLAC，99% 的人用 99% 的设备都听不出来区别。为了这点没人能察觉的区别，文件大 5-10 倍，不值得。
  
  误区二：有损转有损，音质不会差太多。
    大错特错。
    每一次有损压缩，都是一次信息的损失。第一次压 MP3，删掉了一部分你听不到的信息。你再把这个 MP3 拿出来，用 AAC 再压一遍，编码器会再删一遍。两次删的可能不是同一个地方，最后加起来损失就很大了。
    我见过最夸张的，一个视频被群里转来转去，转了七八次，最后画面糊得跟马赛克一样。
    不要反复做有损压缩。源文件尽量存无损，最后输出的时候只做一次有损压缩给用户。

### 编解码的三层境界

  学编解码，你会经历三层境界。
  第一层：看山是山。
    刚入门，觉得压缩就是个黑箱。输入原始数据，输出压缩完的数据。只要参数调对了就行，里面怎么实现的不关我的事。
    90% 用 FFmpeg 的人，一辈子停在这一层。
  
  第二层：看山不是山。
    你开始理解里面的原理。知道 MP3 怎么删你听不到的声音，知道 H.264 怎么做运动估计，知道为什么 CRF 23 是默认值，知道为什么 preset 越慢质量越好。
    遇到问题的时候，你不再是瞎试参数。你知道问题大概出在哪个模块，知道调哪个参数能解决。
    到这一层，你已经超过了 95% 的人。
  
  第三层：看山还是山。
    你不再纠结具体算法的细节。你能站在更高的层面，理解整个编码标准为什么这么设计。为了兼容什么设备，为了适配什么网络，为了平衡什么算力，做出了什么样的取舍。
    你知道每个标准背后的历史，知道哪些妥协是必要的，哪些是历史包袱。
    到这一层，你已经可以参与制定标准了。


## 音频编解码： 

  先讲心理声学模型，然后 MP3、AAC、Opus 逐个拆解，最后讲 3A 算法。

### WebRTC 为什么用 Opus？这个编码到底牛在哪

  做实时音视频的，没人不知道 Opus。所有的视频会议软件——Zoom、腾讯会议、飞书、钉钉，底层的音频编码全都是 Opus。WebRTC 标准把 Opus 设为强制支持的编码。可以说，没有 Opus，就没有今天的实时音视频行业。
  但很少有人说得清楚：为什么 Opus 这么牛？为什么不用 AAC？不用 MP3？不用 G.729？

#### 先搞清楚一个问题：实时通信对音频编码的要求，和普通音乐完全不一样

  你听网易云音乐的时候，编码器可以先缓存 1 秒的音频，慢慢压，压完了再发给你。
  你根本感觉不到这 1 秒的延迟。但实时通话不一样。你对着麦克风说一句话，对方必须在 200 毫秒内听到。
  超过 400 毫秒，你们就能感觉到明显的延迟，对话就不自然了。
  超过 1 秒，就没法正常聊天了。
  所以实时音频编码的要求，和普通音乐编码的要求，优先级是完全反过来的：
    普通音乐编码的优先级：音质第一，压缩率第二，延迟无所谓。
    实时通话编码的优先级：低延迟第一，抗丢包第二，音质排第三。

  这就是为什么 AAC、MP3 虽然音乐压得好，但不适合做实时通话。它们的算法天生就是为了高压缩率设计的，延迟降不下来。
  在 Opus 出来之前，实时通话领域就是一团乱麻：
  - 语音通话用 G.711、G.729、AMR，码率低，但音乐一塌糊涂。
  - 想传高质量音乐用 AAC，但延迟又太高。
  - 想兼顾？那就用两个编码器，检测是语音就切 G.729，是音乐就切 AAC。代码写得想死，切换的时候还会爆音。
 
  直到 2012 年 Opus 出来，这个问题才终于被解决了。

#### Opus 最牛逼的地方：一个打十个

  Opus 的设计目标从第一天就很明确：用一个编码器，搞定所有的音频场景。
  从 6kbps 的超低码率语音，到 512kbps 的无损级音乐，Opus 一个人全包了。
  它是怎么做到的？因为 Opus 根本就不是一个编码器，是两个编码器拼起来的。
      Opus = SILK + CELTSILK 
  是 Skype 搞出来的语音编码器，专门处理人声，在低码率下表现无敌。CELT 是 Xiph 基金会搞出来的音乐编码器，专门处理音乐和复杂声音，延迟特别低。
  Opus 把这两个编码器揉到了一起，还加了个智能切换器：
    - 检测到是纯人声，自动切到 SILK 模式，用低码率。
    - 检测到是音乐或者复杂声音，自动切到 CELT 模式，保证音质。
    - 中间还有混合模式，人声加背景音的时候用。
 切换是无缝的，听众完全感觉不到。你不用再根据场景选编码器了。Opus 帮你搞定一切。

  这就像别人还在纠结买什么车代步，Opus 直接开过来一台变形金刚，能当轿车、SUV、卡车、跑车，还能变飞机。就问你怕不怕。

#### Opus 的三个杀手锏

  1. 杀手锏一：延迟可以低到 5 毫秒
    普通的 AAC 编码，一帧的长度是 23 毫秒。MP3 一帧是 24 毫秒。Opus 最低可以设置成 2.5 毫秒一帧。加上算法本身的延迟，端到端可以做到 5 毫秒。
    5 毫秒是什么概念？比你眨一下眼睛还快。
    当然，最低延迟模式的压缩率会差一点。但你可以自己调：
    - 追求最低延迟：用 2.5ms 帧，适合双人通话。
    - 追求平衡：用 20ms 帧，音质和延迟都不错，WebRTC 默认就是 20ms。
    - 追求最高压缩率：用 60ms 帧，适合网络电台、语音直播。
    从 2.5ms 到 60ms，你可以根据场景自由选。别的编码器根本没这个选项。
  
  2. 杀手锏二：码率动态范围大到离谱

    Opus 支持的码率范围是 6kbps 到 512kbps，横跨两个数量级。
    6kbps 是什么概念？一秒钟 750 字节，一分钟 45KB。一首歌 4 分钟才 180KB。还能听清在说什么。
    512kbps 又是什么概念？已经接近无损音质，和 FLAC 差距很小，普通人听不出来。
    没有任何一个其他编码器能做到这么宽的范围。G.729 最高只有 8kbps，AAC 最低也就 64kbps。Opus 一个顶它们十个。
    更牛的是，Opus 还支持动态码率（VBR）和动态帧率。网络好的时候自动升码率，音质变好。网络差的时候自动降码率，保证不卡。
    整个过程无缝切换，听众听不到任何变化。
    这对移动网络来说太重要了。你用手机开视频会议，在地铁里来回走，网络时好时坏。Opus 会自动跟着调，保证你在信号差的时候也不掉线，信号好的时候音质又能回来。

  3. 杀手锏三：抗丢包能力强

    实时通话，丢包是常态。Wi-Fi 丢个 5%，移动网络丢个 10%，太正常了。
    普通的音频编码器，丢一个包就卡一下，"咔"一声，体验很差。Opus 内置了丢包隐藏（PLC）和前向纠错（FEC）。就算丢了 20% 的包，你也基本听不出来。对方只会觉得声音稍微有点模糊，但完全能听懂，不会卡到断话。
    这个特性有多重要？用过老版本 Skype 的人都知道，网络差的时候，声音断断续续根本没法听。现在你用 Zoom 或者腾讯会议，就算网络卡到视频都不动了，声音往往还能听清。
    这就是 Opus 的功劳。

#### Opus 还有哪些碾压对手的优势

  完全免费，没有专利。
    这一点太重要了。MP3、AAC、H.264 都是有专利的，商用要交钱。Opus 是完全开源免费的，没有任何专利费。你想用就用，想改就改，想卖就卖，不用给任何人一分钱。这也是为什么所有浏览器、所有操作系统都支持 Opus。没有专利风险，大家      都敢用。
  
  音质全面超越 AAC 和 MP3。
    不光是低码下碾压，高码率下 Opus 也比 AAC 好。同样 128kbps，盲听测试 Opus 稳压 AAC 一头，更是甩 MP3 八条街。
  
  复杂度可调。
    CPU 强就开高质量模式，音质更好。CPU 弱就开低复杂度模式，省点电。手机上就可以这么干，插电的时候开高质量，用电池的时候开低复杂度省电。
    
  支持多声道。 
    最高支持 255 个声道。虽然你用不上，但做家庭影院、大型会议系统的人需要。

#### Opus 有没有缺点？

  当然有。
  - 第一：编码质量虽然好，但解码复杂度也高。 比 G.711、G.729 费 CPU。好在现在的手机性能都足够强，这已经不是什么问题了。
  - 第二：硬件支持不如 AAC 好。 很多手机的硬件解码支持 AAC，但不支持 Opus。所以你用手机听歌一般还是 AAC，不是 Opus。但通话的时候都是软解 Opus，也没问题。
  - 第三：文件格式支持不好。 你想存成 .opus 文件，很多播放器还不认。大家更习惯 mp3、m4a。所以在本地存储、下载听歌这个场景，Opus 用的还不多。

  但在实时通话这个领域，Opus 已经是毫无争议的王者。没有任何对手。

  超低速语音通话： 6-16 kbps，20-60ms，SILK
  普通语音通话/会议：16-32 kbps，20ms，SILK或混合
  音乐直播/高音质通话：32-96 kbps，10-20ms，CELT 或混合
  接近无损的音乐：96-256 kbps，10-20ms，CELT
  专业级高质量：256-512 kbps，10ms，CELT

  WebRTC 默认用的就是 20ms 帧、32kbps 左右的 Opus。这个配置是经过千锤百炼的，在音质、延迟、带宽三者之间做到了最好的平衡。你自己做项目直接抄作业就行。
  Opus 这个编码器，是我做音视频这么多年，见过的最接近「完美」的技术产品。

  它几乎满足了人们对一个音频编码器的所有要求：
  - 低延迟 ✔️
  - 高压缩率 ✔️
  - 音质好 ✔️
  - 抗丢包 ✔️
  - 免费开源 ✔️
  - 全平台支持 ✔️
  上一次见到这么全面的技术是什么时候？好像已经想不起来了。
  Opus 基本上把音频编码这条路走到头了。未来十年二十年，大概率不会再有新的通用音频编码能超越它。
  这就是为什么 WebRTC 选了它做标配。这就是为什么所有做实时音视频的公司，最后都会选它。
  你用的每一次视频会议，每一次微信语音通话，背后都有 Opus 在工作。
  你甚至感觉不到它的存在。
  这就是好技术的最高境界。
