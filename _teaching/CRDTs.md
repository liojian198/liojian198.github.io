# 简介

  在以往的经历中，客户端离线数据修改与实现在线的修改数据同步问题，之前做连锁饭店app或者app记账（随手记？），存在的场景是多个店员拿着自己的手机操作app， 可能是没有网的操作，也有web端实时在线操作，这个时候，就会出现app与服务端的数据合并问题，也是最终一致性问题。
还有一个场景， 在IOT/iIOT场景的下，边缘网关或者设备有中控屏操作或者设备在离线的时候可以使用，app也能操作处理，这个时候就会有操作冲突，需要处理操作。具体的场景满大街。以前都是一脸懵的，但是记账的那个是有方案的，但是iot这个就各种坑了。其实收银系统也有这个问题。

## 以往的方案

  实现“手机端离线记账”与“Web端实时操作”的双端数据同步，行业内标准且最优雅的解法是采用“Local-First（本地优先）架构 + 基于操作日志（Operation Log / Delta Sync）的同步引擎”。由于记账场景对数据准确性和无冲突合并有极高要求，这套方案完美契合了前面讨论的分布式数据思想。

整个同步体系的核心设计与落地方案包含以下几个维度：

### 核心架构设计

  两端各自维护独立的本地存储，通过一个中心化的同步网关（Sync Gateway）进行数据对齐。

  客户端架构（双端一致）

    本地数据库：手机端用 SQLite (Room / WatermelonDB)，Web 端用 IndexedDB。它们保证了离线状态下读写秒级响应。

    客户端生成 UUID（关键！）：任何一条新记账记录（如“午饭 30元”）在创建时，必须由客户端在本地生成全局唯一的 UUID，绝不能依赖自增 ID 或服务器返回 ID。这样才能保证离线时创建的记录不会在多端合并时发生 ID 冲突。

    操作日志表（Mutation Log）：客户端不仅存业务数据，还把用户的每一个动作（INSERT、UPDATE、DELETE）记录到一个本地的未同步日志队列中。

  服务端架构

    状态存储与版本管理：服务端维护一个主数据库（如 PostgreSQL），并为每个用户或账本维护一个全局逻辑时钟（如 Lamport Timestamp 或版本向量 Version Vector）。


### 核心同步流程

  1. 场景 A：手机端离线记账 ➡️ 恢复网络后同步到云端与 Web

    离线写入：用户在地铁上（无网）用手机 App 记了一笔账（ID: uuid-001, 金额: 30元）。手机将其写入本地 SQLite，并在本地的 Mutation Log 中追加一条：[PENDING] INSERT uuid-001 at time T1。
    
    网络恢复：手机检测到网络连通，触发同步协议（Sync Protocol）。
    
    Push（推送增量）：手机向服务器发送一个 HTTP/WebSocket 请求，把本地 Mutation Log 中所有未同步的动作包（带上客户端版本号 T1）发给服务端。
    
    Merge（服务端无锁合并）：
    
    服务端接收到 uuid-001 的插入请求，检查主库：如果不存在，直接写入。
    
    服务端更新该用户的账本版本号（例如推进到 V12）。
    
    Acknowledge（确认应答）：服务端返回成功，手机端将本地日志标记为 [SYNCED]。
    
    Broadcast（广播至 Web 端）：服务端通过 WebSocket 实时推送到在线的 Web 端：“有新数据，版本已更新到 V12”。Web 端收到后静默拉取增量并刷新 UI。
  
  2. 场景 B：Web 端实时操作 ➡️ 实时同步到手机端

    实时写入：用户在电脑 Web 端修改了这条账单（把备注从“午饭”改成了“工作餐”）。Web 端向服务端发送 UPDATE uuid-001。
    
    服务端处理：服务端写入主数据库，版本号推进到 V13。
    
    双向触达：
    
    如果此时手机端在线（WebSocket 维持），服务端立刻推送一条通知给手机，手机主动发起 Pull 拉取增量 V12 -> V13，本地更新。
    
    如果手机端离线，服务端暂存变更。等手机下次打开 App 触发同步时，自动把这段时间错过的增量全量拉取。


### 经典冲突解决：如果两端同时改了同一条记录怎么办？

  记账软件中最常遇到的冲突是：手机端离线时修改了某笔账目的金额，而 Web 端在线时同时也修改了同一笔账目的分类。如果不用悲观锁去强行卡死系统，通常采用以下两种工程策略：

    字段级别的 LWW（Last-Write-Wins 寄存器思想）不按“整条记录”来判别冲突，而是精确到字段（Column-level）。每条记录的每个字段都附带一个最后修改时间戳（或混合逻辑时钟 HLC）。
    合并时：如果手机改了金额（时间戳 $T_{mobile}$），Web 端改了分类（时间戳 $T_{web}$），系统会自动将两者的修改进行按字段合并（Merge），最终结果是“新金额 + 新分类”，互不覆盖。
    如果刚好修改了同一个字段，则时间戳更新的胜出。记账领域的天然优势（Append-Only 优先）在记账业务中，绝大多数操作是 INSERT（新增流水）。
    新增流水天然不存在冲突，直接累加即可。对于 UPDATE（修改）和 DELETE（删除），通常采用“软删除（Soft Delete，标记位 is_deleted = true）”。
    配合类似 OR-Set（观察-移除集合）的 CRDT 思想：即使手机离线删除了某笔账，只要另一端在联网时对它进行了有效修改，系统会通过时间戳裁决是“修改后保留”还是“最终删除”，避免物理删除导致的数据不一致。

### 推荐的现成技术栈与工程落地

  如果不想从零手写底层的同步队列和冲突解决逻辑，可以借助现有的现代化成熟工具链：

  前端/客户端本地同步框架：
  
  WatermelonDB（针对 React Native / Web）：性能极佳的离线优先数据库，天然内置了同步引擎（Sync Engine），只需要你实现后端对应的 pull 和 push 接口即可。
  
  RxDB：基于 NoSQL 的离线优先数据库，支持多种复制插件（Replication Plugins），完美对接 CouchDB、GraphQL 或自定义后端。
  
  后端轻量级网关：
  
  可以使用 Go 或 Node.js 编写一个简单的 Delta-Sync 接口：核心逻辑就是接收客户端的 last_pulled_at 时间戳，去数据库把所有 updated_at > last_pulled_at 的账单打包返回给客户端，客户端在本地通过主键（UUID）进行 Upsert 覆盖。


## CRDTs 场景

  什么时候才真正需要用到 CRDTs？
只有当你的记账软件拓展出以下特殊业务形态时，才需要真正应用 CRDTs：

纯 P2P 离线同步：手机和电脑之间没有中心服务器，两台设备直接通过局域网、蓝牙或扫码进行点对点数据对齐。

多人强共享账本：例如“合伙人公司账本”或“大家庭共享账本”，允许多个不同的用户在完全断网的情况下同时修改同一个共享分类、同一笔账单，且要求绝对不能丢失任何人的修改。

对于普通的双端同步记账需求，采用 “客户端 UUID + 本地 SQLite/IndexedDB + 增量同步日志 (Push/Pull)” 即可满足工程落地。
