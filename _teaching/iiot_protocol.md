# 简介

  最近帮小朋友接了个外包，帮他分析需求，发现不少iiot领域的协议，记录下这些协议的信息。

##  modbus rtu

  Modbus RTU 是工业自动化领域应用最广泛的串行通信协议之一。它是经典 Modbus 协议的一种二进制传输模式，专门为工业现场总线（如 RS-485、RS-232）而设计。

以下是对 Modbus RTU 的全方位深度详解：

一、 Modbus RTU 的核心特点
主从架构（Master-Slave）：

网络中只能有一个主设备（Master）（如 PLC、工控机、网关），可以有多个从设备（Slave）（如传感器、电表、变频器）。

从设备永远不会主动发消息，必须等待主设备的查询请求（Query）并给出响应（Response）。

二进制紧凑编码：

与传输文本的 Modbus ASCII 不同，RTU 采用纯二进制数据传输。每个字节由 8 个二进制位组成，空间利用率高，通信速度快。

物理层载体：

通常运行在 RS-485 总线上（支持多机挂载、抗干扰能力强、传输距离远）。

当你在工业现场使用一个 串口服务器（DTU），把底下挂着的一堆 RS-485 Modbus RTU 传感器连上交换机/路由器时，这个过程通常就是 RTU over TCP：

设备侧：传感器和 DTU 之间走的是标准的 Modbus RTU（串口二进制 + CRC）。

网络侧：DTU 把收到的串口二进制字节原封不动地塞进 TCP 的 Payload（负载）里，通过以太网发给你的后端网关。

你的网关收到的：是一串标准的 TCP 字节流，但里面包裹的完全是 RTU 的报文（包含从机地址、功能码、数据和 CRC，没有任何 TCP 专属的长度头）。

## coap 

  CoAP（Constrained Application Protocol，受限制的应用协议）是IETF（特别是CoRE工作组）专门为资源受限的低功耗设备（如物联网传感器、嵌入式节点）和受限网络（如低功耗无线网关、6LoWPAN）设计的一种应用层协议。

如果把传统的 HTTP 比作给服务器之间传输大文件的“豪华大卡车”，那么 CoAP 就是专为物联网微型设备设计的“轻量级电动自行车”——麻雀虽小，五脏俱全。

以下是对 CoAP 协议的全方位深度详解：

核心设计理念与优势
天然的 RESTful 架构（与 HTTP 完美映射）：

CoAP 采用了和 HTTP 一模一样的客户端/服务器（C/S）模型和请求/响应语义（GET、POST、PUT、DELETE）。

这使得 CoAP 能够极方便地与现有的 Web 技术（如 REST API、JSON）无缝融合，甚至可以通过简单的网关实现 HTTP-CoAP 代理转换。

极小的报文开销（Low Overhead）：

传统的 HTTP 报文基于文本，头部动辄几百字节。

CoAP 采用二进制编码，其基础头部（Header）固定只有 4 个字节，再加上简短的选项（Options）和 Token，整个报文体积非常小，能够完美塞进单次 IEEE 802.15.4 等低功耗无线小数据包中。

支持 UDP 传输（内置可靠性机制）：

HTTP 依赖 TCP（三次握手、复杂的拥塞控制、较大的内存开销），这对电池供电、内存仅有几十KB的单片机来说太重了。

CoAP 基于 UDP。为了解决 UDP 不可靠的问题，CoAP 在协议层自己设计了确认机制。

二、 报文类型（Message Types）
CoAP 协议不依赖 TCP 的可靠性，而是通过在 UDP 报文头部标记四种消息类型（Message Types）来保证传输：

CON (Confirmable，可确认消息)：

特点：重要消息。发送方发出后，要求接收方必须回复一个 ACK（应答）。如果没有收到 ACK，发送方会触发指数退避重传机制，直到超时或收到应答。

场景：传感器上报重要数据、开关控制指令。

NON (Non-Confirmable，非可确认消息)：

特点：发后即忘（Fire and Forget）。不需要接收方回复 ACK，丢了就丢了。

场景：高频、连续采集的温度/湿度数据（坏了一帧无所谓，下一秒还会报）。

ACK (Acknowledgment，应答消息)：

特点：专门用来响应 CON 消息的报文，里面通常带有一个对应的 Message ID。

RST (Reset，复位消息)：

特点：当接收方收到一个报文，但因为某种原因（如上下文丢失、无法解析）无法处理时，回复一个 RST 报文，告诉对方“我拒绝/无法处理”。

经典请求/响应与核心特性
1. 报文结构长什么样？
一个 CoAP 报文由以下几个部分紧凑拼装：

Header（4字节）：包含版本号 (Ver)、类型 (T)、标记长度 (TKL)、代码 (Code，如 0.01 代表 GET，0.02 代表 POST，2.05 代表 Content 成功) 以及 16 位的消息 ID (Message ID)。

Token（0~8字节）：用于关联请求和响应。

Options（可选）：类似于 HTTP Header（如 Uri-Path、Content-Type），采用 Delta 编码极度压缩。

Payload（数据载体）：实际的业务数据（如 JSON、CBOR、纯文本或二进制流），前面由一个 0xFF 作为分隔符。

2. 高级特性：观察模式（Observe / Pub-Sub）
这是 CoAP 极为强大的一个特性（对应 RFC 7641）：

传统的 HTTP 需要客户端不断轮询（Polling）服务器：“温度是多少？温度是多少？”。

CoAP Observe 允许客户端向服务器发送一个带 Observe 选项的 GET 请求。

服务器一旦接受，就会建立长连接（或基于 UDP 的状态绑定）。当设备的温度发生显著变化时，服务器会主动、异步地把新数据“推”给客户端，极大节省了电量和带宽。

3. 资源发现（Resource Discovery）
物联网设备通常有很多内部资源（如 /sensors/temp、/actuators/light）。

CoAP 标准规定了一个固定的发现路径：/.well-known/core。

客户端向设备请求这个路径，设备就会返回自己身上所有支持的资源列表，方便网关进行“即插即用”式的自动发现。


通常情况下，CoAP 设备（如传感器、智能插座等物联网终端）在网络架构中扮演的是“CoAP Server（服务端）”的角色。

这与传统的 C/S（客户端/服务端）直觉截然相反。很多人初学 CoAP 时会下意识觉得：“设备是客户端，云端或网关是服务端”。但在 CoAP 的设计哲学中，逻辑正好是反过来的：

为什么物联网设备反而是 CoAP Server？
资源宿主的角度：

在 RESTful 架构中，谁拥有数据资源，谁就是 Server。

物联网传感器（比如温湿度计）拥有温度数据资源（路径如 /sensors/temp）。

网关或云端服务器为了获取这个数据，需要向设备发起 GET 请求。因此，设备是资源的提供者（Server），网关/服务器是请求的发起者（Client）。

设备端如何监听？

尽管 CoAP 基于 UDP（无连接），但设备会在本地监听一个端口（默认 5683）。

网关通过 UDP 向设备的 IP 和端口发送一个带 GET 代码的报文，设备收到后在同一个 UDP 报文中回复 ACK 并带上温度数据。整个过程中，设备在网络层是被动响应的。

特例：什么时候 CoAP 设备会变成“客户端（Client）”？
虽然绝大多数情况下设备是 Server，但在以下特定场景中，设备也会主动发起请求，扮演 CoAP Client：

主动上报（PUSH 模式 / POST 请求）：

如果传感器不是被动等网关来拉数据，而是每隔 10 秒主动把数据“推”给云端，此时设备会向云端（或 CoAP 代理/Collector）发送一个 POST 请求。

在这个动作里，设备变成了 Client，云端/收集器变成了 Server（监听端口接收 POST）。

物联网里的“观察模式（Observe）”：

设备作为 Server，当网关向设备发送一个带 Observe 选项的 GET 请求后，后续数据的流向虽然是设备主动推给网关，但最初的发起方和身份定义上，设备依然是维护资源状态的 Server。

总结
常规拉取场景（Pull）：网关是 Client（发起 GET），设备是 Server（提供资源并响应）。

主动上报场景（Push）：设备是 Client（发起 POST 推送），网关是 Server（接收数据）。

在实际的物联网网关设计中（比如你用 Camel 或 Netty 构建网关），你的网关往往既要作为 CoAP Client 去轮询/拉取设备的数据，同时又要作为 CoAP Server 去接收设备主动 POST 上来的数据。

CoAP 在 UDP 之上自己实现了一套轻量级的可靠传输机制。

由于底层 UDP 是不可靠的（发后即忘，不管丢包），CoAP 协议在其内部划分为“请求/响应层”和“消息层”。消息层（Message Layer）专门负责处理丢包、重传和重复校验，从而在 UDP 之上模拟出了可靠传输。

CoAP 实现可靠传输的核心机制主要包含以下三点：

CON 报文与 ACK 应答
当业务需要确保数据必须送达时，发送方会将报文类型标记为 CON（Confirmable，可确认消息）。接收方收到 CON 报文后，必须立即回复一个 ACK（Acknowledgment，应答消息），并且 ACK 报文中必须携带与原报文完全相同的 Message ID。

超时重传与指数退避（Exponential Backoff）
发送方在发出 CON 报文后会启动一个内部定时器。如果在基础超时时间（通常默认是 2 到 3 秒）内没有收到对方的 ACK，CoAP 会认为包丢了并触发重传。
为了防止网络拥塞，CoAP 采用“指数退避”算法：下一次重传的等待时间会翻倍（例如 2秒、4秒、8秒、16秒）。如果达到最大重传次数（默认通常为 4 次）仍然没有收到 ACK，就会停止重传，并向应用层抛出超时失败。

重复消息去重（Duplicate Detection）
在弱网环境下，接收方其实收到了报文并回复了 ACK，但 ACK 在路上丢失或延迟了。此时发送方超时重传了相同的 CON 报文。接收方依靠报文头部的 16 位 Message ID，能够瞬间识别出这是一个已经处理过的“重复报文”。接收方会静默忽略其业务逻辑（防止一条开灯指令被执行两次），但会再次补发一个 ACK 给发送方。

CoAP 可靠机制与 TCP 的本质区别：
TCP 的可靠是“一刀切”的，无论什么数据都必须建立连接、保证顺序和不丢包，这对物联网设备开销极大。而 CoAP 把选择权交给了开发者：

需要可靠时：发 CON 消息（有重传，保证送达）。

不需要可靠时（如高频传感器持续上报，丢一帧无所谓）：发 NON 消息（发完不管，极其省电和节省带宽）。

这正是 CoAP 协议的标准应用场景之一。在物联网架构中，CoAP 设备（如传感器、智能水表等）直接通过 UDP 连到远端 CoAP 服务端（如云端服务器、IoT 平台或自研网关）是非常经典的组网方式。

设备直接连服务端的实现路径和网络拓扑通常分为以下几种：

1. 直连的网络基础：公网 IP 或 VPN 穿透
如果服务器拥有公网 IP（例如部署在阿里云、AWS 上的后端服务，或者是公网可达的云服务器），设备的 CoAP 客户端可以直接向服务器的公网 IP 和端口（默认 5683）发送 UDP 报文。

如果设备和服务器在局域网内，设备可以直接连服务器的内网 IP。

2. 直连时的通信流程（以主动上报为例）
假设设备要定时向云端服务器上报温度：

设备端（CoAP Client）：打包一个 CoAP 报文（比如 POST /sensors/temp，Payload 为温度数据）。

传输层（UDP）：设备将该报文通过 UDP 协议直接发往云端服务器的 IP:5683。

服务端（CoAP Server）：云端部署的 CoAP 服务（例如基于 Eclipse Californium 或 Camel CoAP 的程序）监听在 5683 端口，收到 UDP 数据包。

响应：服务端解析 CoAP 报文，若采用 CON（可确认）消息，服务端会立即回复一个 ACK（或 2.05 Content 响应），整个直连通信完成。

3. 直连时的典型应用场景
NB-IoT / 4G 蜂窝物联网：运营商的 NB-IoT 模组原生支持 UDP 传输。设备直接通过蜂窝网络将 CoAP 报文发往云端部署的 CoAP Server，由于 NB-IoT 功耗极低、UDP 报文开销小，这种直连模式在抄表、路灯等行业非常普遍。

局域网智慧园区：园区内的传感器通过以太网或 Wi-Fi 直接将 CoAP 数据发给中控室的边缘服务器。

4. 直连时需要注意的痛点
如果设备要直接连公网服务端，通常会面临两个实际工程挑战：

NAT 穿透问题：如果设备处在家庭路由器或局域网的 NAT 后面，服务器无法主动向设备发起请求（因为不知道内网 IP），必须由设备先发起一个请求（或通过 CoAP 的 Registration 机制），在 NAT 上打通一个 UDP 端口映射通道。

安全性问题：互联网上的 UDP 容易受到 DDoS 攻击或窃听。因此在公网直连时，绝不能裸奔使用 CoAP，必须启用其安全版本 CoAPS（基于 DTLS 的加密传输）。


## opc-ua

  OPC UA（Open Platform Communications Unified Architecture，开放式平台通信统一架构）是现代工业自动化和工业物联网（IIoT）领域的“工业通信黄金标准”。

如果说 Modbus 是工业界的“自行车”（轻量、简单但粗糙），那么 OPC UA 就是工业界的“高铁”——它集成了安全性、跨平台、面向对象建模、复杂数据类型以及强大的企业级集成能力于一身。

以下是对 OPC UA 的全方位深度详解：

一、 为什么会诞生 OPC UA？（痛点与背景）
在 OPC UA 出现之前，传统的 OPC（基于微软 COM/DCOM 技术，通常叫 OPC Classic）存在致命缺陷：

死死绑定 Windows 操作系统（因为依赖 DCOM），无法在 Linux、树莓派或嵌入式设备上运行。

防火墙极其不友好，配置 DCOM 端口映射简直是工程师的噩梦。

缺乏统一的数据模型，设备 A 的“温度”叫 Temp，设备 B 可能叫 Temperature，无法做到真正的“语义互通”。

为了解决这些问题，IEC 组织和 OPC 基金会在 2008 年推出了全新的、完全独立于平台的 OPC UA。

二、 OPC UA 的核心架构特征
1. 平台独立性（Platform Independence）
传统的 COM/DCOM 被彻底抛弃。

OPC UA 采用双重传输绑定：

UA TCP 协议（二进制，默认端口 4840）：追求极致性能和低开销，适合底层设备和服务器之间的高速通信。

HTTPS / WebSockets / JSON 协议：适合 Web 端、云端直接调用。

2. 强大的安全性（Security by Design）
安全是 OPC UA 的最大杀手锏，它在协议底层原生集成了一套类似 TLS/SSL 的安全机制：

加密传输：支持 AES-128 / AES-256 对称加密，防止数据被窃听。

数字签名与证书认证：基于 X.509 数字证书，服务器和客户端必须互相验证身份，彻底杜绝“中间人攻击”和非法设备接入。

访问控制（Access Control）：细粒度的用户权限管理（谁能读、谁能写）。

3. 面向对象的信息建模（Information Modeling）
传统协议（如 Modbus）只传冷冰冰的数字（比如“寄存器 40001 的值是 25”）。

OPC UA 是“有灵魂”的：它采用类似面向对象的模型。一个设备在 OPC UA 看来是一个节点（Node），节点不仅有“值（Value）”，还有“元数据（Metadata）”——包括它的单位（℃）、数据类型（Float）、取值范围、甚至设备制造商、型号、状态等。

这使得上位机软件（如 SCADA、MES）能够实现“即插即用”的自动发现和语义解析。

三、 核心通信模式
OPC UA 不仅支持传统的 C/S（客户端/服务端） 模式，还原生支持现代 IIoT 备受推崇的 Pub/Sub（发布/订阅） 模式：

Client / Server 模式（传统查询与订阅）：

客户端主动连接服务器，可以发起 Read（读）和 Write（写）。

数据变更订阅（Monitored Items）：客户端不用傻傻地一直轮询（Polling）。它可以告诉服务端：“当温度变化超过 1 度时，你主动通知我”。这极大节省了网络带宽。

Pub / Sub 模式（物联网大规模组网）：

类似 MQTT，设备（Publisher）可以将数据打包直接广播或发往 Broker（如基于 MQTT 传输的 OPC UA Pub/Sub），多个订阅者（Subscriber）自主消费，非常适合大规模分布式工业物联网。

现代 OPC UA 架构不仅支持局域网内的高速通信，还专门为了“云边协同”和互联网集成做了深度设计。

让 OPC UA 直接连到云端（如阿里云、AWS、私有云服务器），主要可以通过以下几种成熟的方式落地：

1. 核心支撑：OPC UA 的双重网络绑定（Transport Mappings）
很多人以为 OPC UA 只能跑在它专属的内网二进制 TCP 端口（4840）上。实际上，OPC UA 标准协议支持多种传输绑定：

UA-TCP（二进制）：适合局域网高性能通信。

UA-SCADA / UA over HTTPS / WebSockets / JSON：这是 OPC UA 走向云端的关键。它允许将 OPC UA 的请求和结构化数据封装在 标准 HTTPS 或 WebSockets 中，甚至直接编码为 JSON 格式。

这样一来，云端服务器（拥有公网 IP）就可以像调用普通 REST API 或 WebSocket 一样，直接与边缘的 OPC UA 服务端进行通信，无惧公网防火墙和路由器的阻拦。

2. 云端连接的两大主流架构形态
形态 A：云端充当 OPC UA Client（主动拉取或订阅）
拓扑：工厂边缘部署的 PLC 或 OPC UA 网关拥有公网 IP（或通过 VPN/内网穿透打通），云端服务器运行一个 OPC UA Client。

流程：云端 Client 通过 HTTPS 或 UA-TCP 穿透连接到边缘的 OPC UA Server，建立安全的加密会话（基于 X.509 证书），然后直接下发读写指令，或者在边缘侧建立数据变更订阅（Monitored Items）。

特点：云端掌握主动权，但对边缘设备的网络可达性要求较高（边缘端需要有公网 IP 或固定的端口映射）。

形态 B：OPC UA Pub/Sub 模式（主动推送至云端 MQTT Broker，最推荐用于 IIoT）
这是目前工业物联网连接云端最优雅、最主流的做法：

拓扑：边缘侧的 OPC UA 网关（Publisher）将本地设备的面向对象数据转换为 JSON 或 UADP 格式，通过标准的 MQTT 协议主动推送到云端的 MQTT Broker（例如阿里云 IoT Core、EMQX）。

标准支持：OPC UA 官方规范（Part 14）明确定义了 OPC UA Pub/Sub，支持将数据直接映射到 MQTT 消息总线上。

特点：完美契合云原生的“发布/订阅”架构。边缘设备不需要拥有公网 IP，只需像普通物联网设备一样主动连上云端 MQTT 即可，极大地避开了 NAT 穿透和防火墙阻拦的痛点。

3. 直连云端时的安全护城河
因为是直连互联网，安全是生死线。OPC UA 直连云端时，其天生自带的安全机制派上了大用场：

数字证书双向认证：云端和边缘网关必须互相校验对方的 X.509 证书。只有通过白名单认证的合法网关，云端才允许它连入。

端到端加密：所有传输的数据都经过 AES 加密，即使在公网上被抓包也无法破解。

4. 实际项目中的落地建议
虽然 OPC UA 技术上完全能够直接连云端，但在真实的工程实践中，通常不建议让底层的单个 PLC 直接裸连公网云端：

最佳实践：在工厂现场部署一个边缘计算网关（如基于 Java/Netty 或 Python/Node.js 开发的网关）。

让边缘网关在局域网内通过 OPC UA 或 Modbus 聚合所有设备的数据，在边缘侧完成数据清洗、建模和缓存，然后通过安全的 MQTT 或 TLS 隧道将数据统一汇聚到云端。这比让成百上千个底层设备直接连云端要安全、稳定且省带宽得多。
